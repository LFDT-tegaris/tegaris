# Tegaris Application Layer Privacy v0.9.0

**First public source release.**

Status: source published; versioned release in preparation. The source and documentation are available in this repository. The v0.9.0 tag has not yet been published, and no official binaries or container images are available.

## Purpose and audience

This release gives application developers, platform engineers and security reviewers a common source baseline for building and integrating Tegaris. Engineering teams can inspect the architecture, build an isolated workspace, explore the console and run selected tests using synthetic data.

Start with the initial checks below. Broader application integration and operational qualification remain separate work. A source release number does not certify a deployment for production use, institutional data or a particular regulatory requirement.

## Included in the source

- Administration services and console workflows for organizations, principals, workload identities and scoped access.
- Contract and ABI configuration, policy authoring, review and activation interfaces.
- Governed RPC, runtime coordination and evidence components for further integration testing.
- Public configuration and generation inputs, interface definitions, development setup and test tooling.
- Setup, architecture, integration, security, operations, contribution and validation guides.

The presence of a component is not a statement that all of its workflows are qualified. Use the validation status and known issues below when choosing a test.

## Getting-started checks

Use a dedicated Linux VM with systemd and a local Docker Engine. Plan for 32 GiB RAM and at least 130 GiB free disk for the documented image build, with additional capacity for retained environments. Follow the exact tool versions and resource checks in the [setup guide](../getting-started.md). Use synthetic organizations, users, contracts and data.

Each row defines a test to run against the selected installation. Record the observed outcome; the expected result is not a claim that the test has already passed in the institution's environment.

| Test                                    | Procedure                                                                                                                                                              | Expected result and evidence                                                                                                                                                                        |
| --------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| E01: prerequisites                      | Run `bash scripts/operations/policy-testing.sh check` from the selected checkout.                                                                                      | The prerequisite check passes. Record the revision, operating system and exact tool versions. No application services are started by this check.                                                    |
| E02: locked dependencies                | Follow the setup guide's dependency installation with a private data directory outside the checkout.                                                                   | Installation completes without changing dependency locks. Retain its log and the chosen data-directory location privately.                                                                          |
| E03: service build and initialization   | Build the seven service images, then run `qa-start --local-qa-fixture` and `qa-status` as documented.                                                                  | The build finishes successfully and the expected long-running services are healthy. Record image identifiers and the startup result. Initialization does not prove application-request enforcement. |
| E04: workspace access                   | Use a generated synthetic account, complete authenticator registration and select its organization.                                                                    | The console identifies the intended account and workspace. Record sign-in or verification errors without sharing credentials or authentication material.                                            |
| E05: console inspection                 | Follow the [console guide](../user-guide/README.md) to inspect navigation, resource lists, forms and status displays. Include an empty list and an invalid form input. | Controls have understandable labels; loading, empty and error states are visible; selected organization context remains clear. Record unavailable flows as open.                                    |
| E06: documentation and component checks | Run the commands below after completing their prerequisites.                                                                                                           | Each selected command exits successfully. Retain failures with the exact command and revision; a component pass does not establish an end-to-end application result.                                |

Start E06 with the documentation check, which does not start services:

```sh
python3 scripts/docs/check-docs.py
```

On a dedicated machine, with the pinned Node.js version and dependencies installed, the sign-in page tests exercise a temporary synthetic identity provider:

```sh
node --test tests/integration/local-runtime/oidc-signin.test.mjs
```

For further tests, use the [testing guide](../development/testing.md). Select tests according to the behavior being checked and account for any retained services before allocating build or test resources. The policy activation/withdrawal helper and the full runtime journey are broader checks, not prerequisites for completing E01–E06.

For every test run, retain the source revision, commands, tool versions, expected result, actual result and a status of **passed**, **failed** or **not run**. Keep account files, keys, logs containing sensitive data and infrastructure details in the institution's approved systems. Public reports should use a minimal synthetic reproduction.

## Validation status

The public-source baseline has a successful clean Linux initialization result, including the seven service images. Later changes have received focused checks, including selected console formatting, lint, types and tests, and runtime compilation and transport tests. These are distinct results with different scopes.

Documentation checks pass on the public repository. The full CI workflow currently stops at its runner-configuration prerequisite; its quality and runtime integration jobs have not run. The earlier focused results do not establish a passing public CI suite.

The [hosted demonstration](../demo.md) supports three permitted contract reads: payment details, settlement workflow data and a restricted reference value. It also demonstrates rejection of an unapproved method, an unassigned contract and a missing application assertion. This coverage is limited to the six documented examples. Validation is limited to the checks described here. A complete production, performance, security, accessibility or institutional-integration qualification is not claimed.

## Known issues and limits

### Synthetic balance-read workflow remains unqualified

In the separate balance-read integration check, an intended permitted synthetic balance read returned HTTP 403 with an authorization-denied result. No provider call was observed. The paired unapproved-method request was also denied without a provider call, as expected.

The cause and resolution remain open, and no supported workaround is documented. This result does not establish that every topology fails identically. Applications that depend on this balance-read workflow must treat it as unavailable until a correction has passed the corresponding integration test. Do not disable authorization checks to work around the denial.

### Time-limited development authority

The local fixture uses time-limited synthetic authority and credentials. Setup and build time consume part of that window. Restarting services or signing in again does not renew all underlying authority. Read the [hosted development environment guidance](../development/hosted-demo.md) before planning a persistent environment or scheduled demonstration.

### Expired runtime-profile requests

Continuation of an expired runtime-profile request has only partial validation. Checks cover stale targets, foreign privacy context and consumed requests; successful continuation, duplicate/replay handling, rejection of already-bound requests and concurrent attempts have not been qualified for this operation. Treat that continuation path as unsupported in v0.9.0. Preserve the original request and its result when reporting a failure; creating replacement requests is not a documented workaround.

### Experimental administration CLI

The source tree retains an experimental administration CLI for contributors. It is excluded from the supported v0.9.0 administration surface and default release checks. Use the console for the documented user workflows; see the [CLI development notes](../../apps/admin-cli/README.md) for its incomplete commands and opt-in checks.

### API reference coverage

The published OpenAPI definitions do not yet cover every administrative extension. Check the [interface reference](../reference/interfaces.md) before generating a client; do not assume an omitted operation is supported by a generated SDK.

### Further qualification

Event-backed visibility, some integration scenarios, production key custody, certificate continuity, recovery, retained-state upgrades, performance and availability require additional evidence for the selected deployment. The [validation guide](../evaluation/README.md) describes those assessments. They are not implied by completing the basic checks above.

## Compatibility and upgrades

v0.9.0 is planned as the first versioned source release. It provides no supported upgrade path from unpublished development installations. Start a separate isolated workspace and preserve earlier environments according to their operator's procedures.

When published, the v0.9.0 tag will identify a fixed source snapshot. Component package versions, API versions, database revisions and policy versions have separate meanings and need not use the same number. The 0.x public API may change; subsequent release notes must describe compatibility and migration requirements.

Published release contents are immutable. Corrections will receive a new release identifier. Use documentation from the same tag as the source being used.
